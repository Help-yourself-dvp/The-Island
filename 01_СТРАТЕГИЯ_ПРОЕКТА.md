# 01 — СТРАТЕГИЯ ПРОЕКТА И AI-РАЗРАБОТКИ

## 1. Назначение документа

Этот документ определяет техническую и организационную стратегию нового мобильного игрового проекта.

Он является частью набора из четырёх документов:

1. `01_СТРАТЕГИЯ_ПРОЕКТА.md`
2. `02_КОНЦЕПЦИЯ_ИГРЫ.md`
3. `03_СЮЖЕТ_И_ТЕКСТЫ.md`
4. `04_MASTER_PROMPT.md`

AI-агент обязан прочитать ВСЕ четыре документа перед началом реализации.

Если документы уточняют друг друга:

- стратегия определяет инженерные границы;
- концепция определяет игру;
- сюжет определяет повествование;
- MASTER_PROMPT определяет процедуру реализации.

Нельзя начинать писать код после прочтения только одного документа.

---

# 2. ЭТО НОВЫЙ ПРОЕКТ

Проект создаётся в НОВОМ GitHub repository.

Не создавать его как development branch SKYFORGE.

SKYFORGE является отдельным экспериментальным проектом и сохраняется без изменений.

Причина:

новая игра имеет принципиально меньшую техническую сложность и другую архитектуру.

SKYFORGE ориентирован на:

- physical sandbox;
- Rapier;
- dynamic rigid bodies;
- machine construction;
- procedural ecosystem;
- сложную физику.

Новый проект ориентирован на:

- компактный красивый мир;
- понятный resource loop;
- строительство;
- восстановление острова;
- автоматических работников;
- постепенное открытие зон;
- большое количество визуального feedback;
- простое управление;
- стабильную мобильную производительность.

Не переносить архитектурную сложность SKYFORGE без необходимости.

---

# 5. ГЛАВНАЯ ИНЖЕНЕРНАЯ ФИЛОСОФИЯ

Новая игра должна выглядеть сложнее, чем она устроена внутри.

Это намеренное решение.

Не моделировать физически то, что можно убедительно показать визуально.

Пример.

НЕ:

17 физических брёвен с rigid bodies лежат на спине героя.

А:

game state:

wood = 17

render state:

визуальная стопка из нескольких брёвен растёт в зависимости от wood.

НЕ:

рабочий симулируется полноценным character controller + сложной физикой.

А:

worker:
state machine
+
navigation/steering
+
animations.

НЕ:

строящееся здание физически состоит из сотен деталей.

А:

constructionStage:
0 → 1 → 2 → 3 → completed

и визуальная модель меняется по стадиям.

Игрок должен воспринимать результат как живой мир.

Внутренняя реализация должна оставаться простой.

# 6. ЦЕЛЬ

СДЕЛАТЬ ЗАКОНЧЕННУЮ ПРИЯТНУЮ ИГРУ,
а не технологическую демонстрацию.

Качество важнее количества систем.

Предпочтительно:

15 хорошо реализованных вещей

вместо:

100 систем-заглушек.

# 7. ЦЕЛЕВАЯ ПЛАТФОРМА

Основная:

Android.

Главное тестовое устройство:

Honor Magic 8 Pro.

Управление:

touch-first.

Не требовать:

- аккаунта;
- сервера;
- регистрации;
- постоянного Internet;
- рекламы;
- аналитики.

# 8. ФОРМАТ ЭКРАНА

Основной вариант проекта:

LANDSCAPE.

Причина:

- больше пространства для локации;
- удобно видеть работников;
- лучше подходит строительству города;
- можно отображать несколько процессов одновременно;
- меньше UI перекрывает игровой мир.

Если дальнейшее тестирование покажет, что portrait существенно лучше соответствует game loop, это можно отдельно рассмотреть позже.

В первой архитектуре ориентироваться на landscape.

---

# 9. ВИЗУАЛЬНАЯ ЦЕЛЬ

Не стремиться к:

- photorealism;
- AAA;
- Unreal-like rendering;
- сложным лицам;
- cinematic realism.

Цель:

POLISHED STYLIZED MOBILE GAME.

Характер:

- яркая;
- тёплая;
- чистая;
- хорошо читаемая;
- округлая;
- приятная;
- оптимистичная.

Визуальная сложность достигается:

- качественными моделями;
- согласованной палитрой;
- хорошим lighting;
- мягкими shadows;
- эффектами;
- анимацией;
- окружением;
- feedback.

Не использовать примитивные procedural shapes как принцип всего мира, если доступен качественный легальный game-ready asset.

---

# 10. ASSET STRATEGY

В отличие от SKYFORGE, новый проект НЕ обязан быть procedural-only.

Разрешены внешние игровые assets.

Предпочтение:

CC0 / Public Domain.

Допустимы другие лицензии только после явной проверки возможности:

- коммерческого использования;
- модификации;
- распространения внутри игры.

Запрещены:

- ripped assets;
- assets из чужих коммерческих игр;
- неизвестное происхождение;
- «free download» без понятной лицензии;
- NonCommercial, если потенциально планируется распространение/монетизация;
- содержимое, которое нельзя законно распространять.

---

# 11. ASSET PROVENANCE

Создать:

`docs/ASSET_LICENSES.md`

Для внешнего asset хранить:

- название;
- автор;
- источник;
- URL;
- license;
- дата получения;
- назначение.

По возможности сохранять LICENSE исходного pack.

Приоритет источников:

1. авторские GitHub repositories с ясной лицензией;
2. CC0 game asset creators;
3. Kenney;
4. Quaternius;
5. другие проверенные sources.

Poly Haven использовать преимущественно для:

- HDRI;
- отдельных материалов,

а не как библиотеку тяжёлых 250MB моделей для mobile game.

# 12. GAME-READY ВАЖНЕЕ PHOTOREAL

Предпочтительнее:

5 качественных game-ready деревьев

чем:

1 photogrammetry tree на 250MB.

Предпочтительнее:

единый art style.

# 13. НЕ НУЖНО СОТНИ МОДЕЛЕЙ

Для одной зоны достаточно примерно:

- 4–6 trees;
- 4–8 rocks;
- 3–6 bushes;
- 4–8 small plants;
- 2–4 logs/stumps;
- несколько building modules;
- несколько props.

Разнообразие создаётся:

- scale;
- rotation;
- color variation;
- placement;
- grouping;
- animation;
- material variation.

# 14. ФОРМАТЫ

Приоритет runtime:

GLB / glTF.

Но OBJ/FBX pack НЕ считается автоматически непригодным.

Если conversion можно выполнить:

- agent-side;
- CLI;
- GitHub Actions;
- автоматизированным script,

то пользователь НЕ должен устанавливать Blender вручную.

Не требовать от пользователя профессионального 3D-software.

creative director;

Техническую работу выполняет AI-agent.

# 16. РОЛЬ AI-АГЕНТА

AI-agent выполняет:

---

# 17. GIT STRATEGY

Основная ветка:

`main`

должна всегда содержать последнюю принятую стабильную версию.

Большие эксперименты выполнять отдельно.

Например:

`experiment/environment-pack`
`experiment/new-lighting`
`experiment/character-pack`

Не разрушать working build ради эксперимента.

Эксперимент сначала сравнивается.

После принятия:
merge.

После отказа:
main остаётся рабочим.

---

# 18. DEVELOPMENT STRATEGY

Не пытаться реализовать весь остров за один огромный AI-заход.

Разработка идёт вертикальными slices.

Первый slice обязан доказать:

MOVE
→ CUT
→ COLLECT
→ CARRY
→ DELIVER
→ EARN
→ BUILD
→ WORLD CHANGES.

Только после того, как этот цикл:

- приятен;
- визуально понятен;
- стабилен;
- работает на телефоне,

добавляется следующая зона.

---

# 19. QUALITY GATE ПЕРЕД РАСШИРЕНИЕМ

Нельзя добавлять следующую большую location, если текущая:

- выглядит как debug prototype;
- регулярно зависает;
- имеет сломанную camera;
- имеет раздражающее управление;
- не даёт ясного feedback;
- имеет непонятную экономику.

Сначала polish.

Потом content expansion.

---

# 20. НЕ НУЖНА СЛОЖНАЯ ФИЗИКА

Использовать physics только там, где она реально добавляет удовольствие.

Большая часть игры может использовать:

- collision tests;
- raycasts;
- simple movement;
- triggers;
- steering;
- scripted animations.

Не подключать Rapier автоматически.

Если character и world хорошо работают без полноценного rigid-body engine:
это предпочтительно.

---

# 21. AI WORKER ARCHITECTURE

Workers не требуют сложного AI.

Достаточно состояний:

IDLE
GO_TO_RESOURCE
WORK
PICKUP
GO_TO_DESTINATION
DELIVER
RETURN.

Navigation:

waypoints;
simple path graph;
steering.

Не нужен сложный open-world navmesh, если карта специально спроектирована под простые маршруты.

---

# 22. ECONOMY ARCHITECTURE

Экономика должна быть data-driven.

Пример:

resource:
WOOD
STONE
FOOD
COINS

building:
SAWMILL

upgrade:
cost
effect
visualStage

Не разбрасывать баланс magic numbers по gameplay code.

---

# 23. BUILDINGS

Building является stateful entity.

Например:

RUIN
REPAIRED
LEVEL_1
LEVEL_2
LEVEL_3

Каждая стадия:

- имеет цену;
- визуально отличается;
- меняет gameplay;
- открывает что-то новое.

Игрок должен видеть физическое изменение мира после покупки.

---

# 24. SAVE

Прогресс обязательно сохраняется локально.

Сохранять:

- открытые зоны;
- resources;
- coins;
- buildings;
- upgrades;
- workers;
- story progress;
- player position при необходимости;
- settings.

Игра не должна требовать cloud account.

---

# 25. НИКАКОЙ РЕКЛАМЫ

Проект изначально проектируется без:

- interstitial ads;
- rewarded ads;

- ad SDK.

---

# 26. НИКАКОГО PAY-TO-WIN

Вся основная игра должна быть доступна через gameplay.

Не создавать:

- premium currency;
- energy;
- gems;
- loot boxes;
- paywalls.

---

# 27. ВОЗМОЖНАЯ МОНЕТИЗАЦИЯ — НЕ СЕЙЧАС

Первый релиз проектировать без monetization SDK.

Если проект позже получает аудиторию, отдельно рассмотреть:

- добровольную поддержку;
- donation;
- optional supporter edition;
- благотворительную модель.

Это отдельная юридическая/продуктовая задача.

Не внедрять её автоматически.

---

# 28. OFFLINE FIRST

После установки основные функции полностью работают без Internet.

Никакой обязательной сети для:

- запуска;
- save;
- progression;
- assets;
- gameplay.

---

# 29. PERFORMANCE

Приоритет:

smoothness > максимальные графические эффекты.

Honor Magic 8 Pro:
цель около 60 FPS.

Но архитектура не должна бессмысленно требовать flagship.

Использовать:

- instancing;
- shared materials;
- LOD при необходимости;
- pooled effects;
- bounded worker count;
- simple AI updates.

---

# 30. CAMERA

Камера специально проектируется под game design.

Не нужна свободная сложная камера SKYFORGE.

Предпочтительно:

контролируемая third-person/isometric hybrid camera.

Она должна:

- красиво показывать уровень;
- не проходить под землю;
- не застревать в деревьях;
- не требовать от игрока постоянно бороться с ней.

Рассмотреть фиксированный или ограниченный yaw.

Это значительно упрощает level composition.

---

# 31. УПРАВЛЕНИЕ

Главное:

один virtual joystick.

Большая часть действий контекстная/автоматическая.

Пример:

подошёл к tree
→ автоматически начинает рубить

или появляется одна большая contextual action button.

Подошёл к delivery zone
→ cargo автоматически разгружается.

Подошёл к upgrade pad
→ показывается цена.

Не создавать HUD с 7 постоянными кнопками.

---

# 32. UI

Минимальный HUD:

coins;
главный resource/cargo;
objective;
pause/settings.

Не перекрывать мир.

Крупные touch targets.

Визуально:
clean mobile game.

---

# 33. GAME FEEL ВАЖНЕЕ СИМУЛЯЦИИ

Когда дерево рубят:

- дерево реагирует;
- появляются chips;
- камера слегка отвечает;
- звучит impact;
- progress понятен;
- дерево падает/исчезает красиво;
- logs появляются с satisfying animation.

Не требуется физически идеально симулировать каждую щепку.

Игрок должен ощущать действие.

---

# 34. WORLD RESPONSE

Каждая важная покупка должна менять остров.

Пример:

до:
сломанная лесопилка.

после:
работающая лесопилка;
движется механизм;
появляется worker;
горит свет;
появляется storage;
меняется музыка/ambient;
открывается pathway.

Прогресс должен быть визуальным, а не только числом.

---

# 35. НИКАКИХ ИСКУССТВЕННЫХ ТАЙМЕРОВ

Не использовать:

«ждать 4 часа»;
«приходи завтра»;
energy cooldown.

Если строительство занимает время:
это несколько секунд красивой animation внутри активной игры.

---

# 36. STORY

Игра имеет лёгкий сюжет.

Но gameplay не должен постоянно останавливаться ради длинных диалогов.

История передаётся:

- короткими репликами;
- visual change;
- environment;
- несколькими персонажами;
- короткими story beats.

Подробности определены в:

`03_СЮЖЕТ_И_ТЕКСТЫ.md`.

---

# 37. ДОКУМЕНТАЦИЯ ДЛЯ БУДУЩИХ AI

Каждый значимый архитектурный выбор записывать.

Не заставлять следующего AI угадывать:

- почему выбран asset;
- почему не используется physics engine;
- как работает worker;
- где balance;
- как добавить zone;
- как добавить building.

AI_GUIDE должен оставаться актуальным.

---

# 38. DEFINITION OF ENGINEERING SUCCESS

Проект успешен технически, если пользователь без разработки на своём компьютере способен:

1. открыть GitHub;
2. получить APK из Actions/Release;
3. установить его на Honor Magic 8 Pro;
4. играть offline;
5. сообщить AI о проблеме;
6. получить исправленную APK после следующей итерации.

Это и есть основной development pipeline проекта.

---

# 39. ГЛАВНЫЙ ПРИНЦИП

Не пытаться доказать, что AI способен построить максимально сложную игру.

Нужно построить хорошую игру.

При выборе между:

REAL SIMULATION

и

CONVINCING ILLUSION

если игрок практически не видит разницы:

использовать CONVINCING ILLUSION.

Сэкономленное время направить на:

ART
ANIMATION
FEEDBACK
CONTENT
POLISH
STABILITY.

Результат должен восприниматься намного богаче, чем его внутренняя техническая сложность.
